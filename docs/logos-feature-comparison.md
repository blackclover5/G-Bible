# G-Bible and Logos Bible Software: feature comparison

**Purpose:** Use Logos as a functional benchmark for G-Bible's study workflows and usability, not as a design, branding, or implementation template. This is a source-code and UI inventory of the supplied G-Bible project compared with Logos' published desktop feature matrix. A feature marked *partial* is not necessarily broken; it means G-Bible has a related workflow but does not establish full Logos-equivalent scope, data coverage, or polish.

**Reference checked:** Logos Help Center, [Logos Platform Comparison](https://support.logos.com/hc/en-us/articles/9785956686349-Logos-Platform-Comparison) (accessed 2026-11-08). Related official guides: [Using Guides](https://support.logos.com/hc/en-us/articles/360017893592-Using-Guides), [How Do I Search in Logos?](https://support.logos.com/hc/en-us/articles/360039621591-How-Do-I-Search-in-Logos), [Get Oriented in Logos](https://support.logos.com/hc/en-us/articles/360036135712-1-Get-Oriented-in-Logos), and [Get started with Logos for free](https://support.logos.com/hc/en-us/articles/360023029051-Get-started-with-Logos-for-free).

## Status key

- **Present** — a corresponding feature or workflow is exposed in G-Bible's UI/source.
- **Partial / data-dependent** — a related capability exists, but depth depends on installed modules, tagging, configured services, or is narrower than Logos.
- **Not identified** — no equivalent was identified in the supplied project. This is a gap candidate, not a claim that it could never be added.

## What G-Bible already does especially well

- **Local-first ownership:** G-Bible stores its library and personal study material on the user's computer and can work offline after resources are installed.
- **Open resource formats:** The project includes importers/readers for multiple open Bible and book formats, rather than relying only on one proprietary library ecosystem.
- **Workspace flexibility:** Multiple resources, tabs, resizable panes, link sets, and saved layouts are already core concepts.
- **Broad study toolbox:** Timelines, maps, genealogies, harmonies, outlines, concordance, word lists, clause/dependency tools, sermon tools, reading plans, prayer lists, notes, and memorization are represented in the project.
- **User-controlled sync and AI:** Sync targets and AI providers are configured by the user rather than being mandatory cloud dependencies.

## Highest-value gaps to prioritize after the UI refresh

1. **Unified discovery:** Make every resource, tool, guide, document, and action findable from one command/search surface with clear categories and keyboard navigation.
2. **Consistent guides:** Give Passage, Word, Exegetical, Topic, and Sermon workflows a consistent input, results, section navigation, and save/reopen model.
3. **Contextual actions:** Keep the right-click menu short at the top (copy, note, highlight, search, guide) and move specialist actions into clearly named groups, without removing advanced actions.
4. **Library metadata and filters:** Improve filtering by resource type, author, language, source, and installed status; clearly explain when a study result needs a tagged resource.
5. **Resource-aware study:** Show which installed modules support each guide/search and distinguish “no result” from “required resource not installed.”
6. **Reliability and test coverage:** Add seeded browser tests for menu behavior, pane linking, notes/highlights, resource import, search, sync conflict handling, and keyboard navigation.
7. **Desktop packaging:** Keep the local service architecture, but provide a native desktop shell only after the web UI and local data lifecycle are stable.

## Important parity caveat

Logos' published desktop feature matrix describes features in its own commercial resource and dataset ecosystem. G-Bible cannot provide equivalent commentary coverage, reverse-interlinear tagging, Factbook breadth, or semantic search quality merely by adding a button; those capabilities require compatible, licensed or openly redistributable content and indexes. G-Bible should explain missing data clearly and remain honest about partial results rather than imply that a tool is equivalent when the underlying corpus is absent.

## Desktop application and synchronization notes

The supplied source has a `run.py --desktop` path that attempts to host the local web app in a PyWebView native window and falls back to the browser if PyWebView is unavailable. The README describes a Linux AppImage, but the supplied archive does not include an AppImage build recipe or Windows packaging workflow; its Windows section still describes Windows as planned. Therefore, the native desktop experience is an available launch mode, not yet a complete, reproducible Linux-and-Windows release pipeline. The sync documentation describes local-folder, WebDAV, and Nextcloud targets. This is a useful local-first foundation, but sync reliability still needs multi-device/conflict testing before claiming production-grade parity with Logos' account-based cross-device sync.
